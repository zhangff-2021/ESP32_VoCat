# 转设备：下行呼入通知与房间票据握手

适用工程：`ESP32_VoCatXKorvo`。
2026-11-22 新增，与平台侧《设备侧「转设备」协议契约》同步冻结。
平台侧权威文档在 livekit 仓 `docs/DEVICE-TRANSFER-PROTOCOL.md`。
平台侧决策依据：livekit 仓 `docs/adr/0035-transfer-to-device-bridges-in-same-room.md`（ADR-0035）
与 `docs/adr/0037-multi-party-transfer-first-answered-wins.md`（ADR-0037，多方转接）。
⚠️ 本工程工单在 livekit 仓 `.scratch/transfer-to-device/issues/07-firmware-transfer-support.md`。

## 这条通知是什么

通话中有人说「转前台小智」时，平台给**那台设备**发一条 MQTT 通知，
设备拿通知里的**房间票据**连 WebSocket，**加入客户正在通话的那个房间**，
与设备背后的人直接对话。

```text
客户 ──SIP/浏览器/设备A──> 网关(主叫腿) ──> LiveKit 房间 ──> 智能体
                                                     ▲
                                                     │ 加入既有房间
                        平台 ──MQTT 通知──> 设备B ──WS(带票据)──┘
```

⚠️ **方向和提醒相反**：

| | 提醒 | 转设备 |
| --- | --- | --- |
| 进哪个房间 | 设备自己建的新房间 | **客户正在通话的那个房间** |
| 房里有谁 | 智能体 | 客户 + 原来的智能体 + 设备B |
| 设备播什么 | 智能体播提醒内容 | **设备不播内容** |
| 智能体何时退出 | 播完/确认后 | **设备B 入房成功后** |

## 多方转接（设备侧无感）

客户可能说「把张三和前台小智一起拉进来」—— 一次转接里含**多个**目标
（平台侧决策见 ADR-0037）。

对设备侧**完全无感**：平台**逐目标**发通知，设备只收到**自己那一条**，
报文格式与单目标时**完全一致**。设备**不需要**支持"多个目标"，
也不需要知道还有别人被转接了；多个设备同时被转时各自独立收通知、独立入房。

⚠️ 客户那头**只听得到一路**（平台网关不混音）—— 客户听到的是先应答的那位，
其余与会者在客户那头听不到。设备侧不需要做什么，
但现场要知道这个限制，别当成"声音断了"。

## 与本工程现有规则的关系

本工程当前的规则是「平台直接向当前 WebSocket 推送音频」「设备不再发布
`devices/{id}/ack`」「重复业务由平台处理」（见 `device-mqtt.md`）。
**转设备完全沿用这些规则**，只多两件事：

1. **多订一个 MQTT 主题**（`devices/{id}/transfer`）；
2. **WS 握手多带一个字段**（房间加入票据）。

其余（不进新房间、不播内容、不回 ACK）都不变。

## 一、握手：多下发一个订阅主题

平台会在握手响应的 `mqtt` 里多下发一个 `transfer_subscribe_topic`
（值形如 `devices/{device_id}/transfer`）。

- `subscribe_topic` 仍然是 `devices/{device_id}/task`（提醒），**语义不变**；
- `transfer_subscribe_topic` 是**新增的可选字段**：老平台不下发时设备照旧工作，
  这样固件可以**先于**平台上线；
- 设备要多订这一个主题（见下）。

⚠️ **不加这个订阅会怎样**：平台投递转接通知时 broker 拒绝该主题 ——
而 broker **不会因为订阅被拒就踢连接**，所以表现是：
MQTT 正常在线、状态正常上报、提醒照收，**只有转接通知永远不来，零报错**。

## 二、订阅：多订一个主题

### 2.1 只订提醒主题的老设备

`device_handshake.c` 现在把 `subscribe_topic` 的期望值**写死**成
`devices/{id}/task`。新增 `transfer_subscribe_topic` 后，
校验要**改成两者分别校验**：少了转接主题只是不支持转接，不该让设备握手失败。

### 2.2 订阅被拒的表现

`transfer_subscribe_topic` 订不上时（broker 只放行一个主题）：
**连接仍在**、提醒照收。设备要把这种情况记下来
（"本设备不支持转接"），别无限重连 —— 提醒链路是好的，重连只会把它也弄坏。

## 三、新增转接通知解析分支

现在 `device_mqtt_parse_task()` 判死 `kind == "reminder"`，
其余**整份拒收**。转接通知会因此被静默丢弃。

新增独立的解析函数，主题是 `devices/{id}/transfer`，载荷：

```json
{
  "kind": "transfer",
  "transfer_id": "tr-20261122-0007",
  "room_name": "sip-8613800001234",
  "ticket": "v2.<payload>.<sig>",
  "expires_at": "2026-11-22T10:03:20Z",
  "timeout_sec": 30
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `kind` | 是 | 恒为 `"transfer"` |
| `transfer_id` | 是 | 不透明字符串，只作日志/排查用 |
| `room_name` | 是 | 要加入的既有房间 |
| `ticket` | 是 | 房间加入票据，**一次性**、TTL 约 120s |
| `expires_at` | 是 | 票据过期时刻（UTC） |
| `timeout_sec` | 否 | 平台等待设备入房的窗口 |

⚠️ **不要**在提醒解析器里放宽 `kind` 判断 —— 那会让提醒路径接受转接载荷。

## 四、WS 握手：带房间加入票据

设备收到转接通知后，用**同一个 `ws_service`** 起会话，但要加入**既有房间**：

- 现有 WS auth 帧是 `proto_build_reminder_auth_frame(...)`（提醒场景，"起一个新会话"）；
- 转接场景需要**第三种** auth 帧：带 `join_ticket` 的那种。

`ticket` 是 `v2` 前缀（平台侧控制台票据是 `v1`），**一次性、120s**。
⚠️ **票据只能用一次**：用掉即焚；失败重试要**重新拿票据**，不能重放。

设备**不播内容、不改音轨、不建新房间**：进了既有房间之后，
房间里的人（客户 + 原智能体）就是它的对话对象，智能体在设备入房后退出。

⚠️ 票据过期就**丢弃本次转接**并上报"票据过期"，
**不要无限重试**（重试必然还是失败）——记一条 ERROR 日志、丢弃本次转接、
让平台回退到智能体。

## 五、通话中收到转接通知

⚠️ **不要打断当前通话。** 提醒的语义是「排到空闲再播」，
转接的语义是「现在就有人要跟你说话」—— 但**打断客户正在进行的通话**代价更大。

处理：记一条日志（`transfer dropped: busy`），**丢弃本次通知**。
平台侧会在超时后判为「已通知但无人接听」。

## 六、版本门槛（固件要能报出支持转接的版本）

平台侧会做**版本门槛**：设备上报的 `firmware_version` 低于支持转接的版本时，
**在发起转接之前就拒**，并让智能体明确告诉客户"该设备固件版本过旧，不支持转接"。

⚠️ 不能笼统说"无人接听"——否则现场会把版本问题误判成设备坏了。

因此固件上报的 `firmware_version` **要能区分出支持转接的版本**。

## 七、回声（已知限制，本期不解决）

转设备后，主叫设备 A 与被转设备 B 在**同一个房间**里，
若 A 的麦克风拾到 A 的扬声器放出来的 B 的声音，B 会听到自己的回声。

⚠️ **本期不做平台侧回声消除**。规避办法是设备侧开 AEC，或人工用耳机。

## 八、联调清单

- [ ] 握手能解析到 `transfer_subscribe_topic`（老平台没有该字段时不报错）。
- [ ] 设备订阅了 `devices/{id}/transfer`，SUBACK granted。
- [ ] 转接主题被拒时连接仍在、提醒仍能收到、不无限重连。
- [ ] 收到 `kind == "transfer"` 能解析出 `room_name` + `ticket`。
- [ ] 缺字段 / `kind` 未知时**整份拒收**（现有行为保持）。
- [ ] 带票据起 WS 能进入**指定的既有房间**，且不再收到提醒类的 auth 任务列表。
- [ ] 票据用过第二次时被拒（一次性）。
